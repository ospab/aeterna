# Системные вызовы: объекты, дескрипторы, IPC

Реализация: `core/object.rs` (логика) и `core/syscall/objects.rs` (обвязка). Обёртки для программ
лежат в `user/liboos/src/ipc.rs` (IPC), `user/liboos/src/mem.rs` (память) и
`user/liboos/src/hw.rs` (прерывания, порты, DMA). Остальные вызовы (write, mmap, ...) описаны в
`core/syscall/mod.rs`.

## Соглашение

`SYSCALL`: номер в `RAX`, аргументы в `RDI, RSI, RDX, R10, R8`, результат в `RAX`.
`RCX` и `R11` затираются. Отрицательный результат — ошибка:

| код | имя | смысл |
|---|---|---|
| -1 | InvalidSyscall | нет такого вызова |
| -2 | PermissionDenied | у дескриптора нет нужного права |
| -3 | InvalidArgument | неверный аргумент (длина > 128, повтор дескриптора, ...) |
| -5 | Busy | очередь канала полна |
| -6 | OutOfMemory | нет страниц, нет свободного диапазона адресов, таблица объектов полна |
| -7 | NotSupported | объект этого не умеет (например, `mem_phys` у обычной памяти) |
| -9 | NoSuchProcess | |
| -10 | BadAddress | указатель вне пространства процесса |
| -11 | BadHandle | значения нет в таблице (не выдавалось, закрыто, устарело) |
| -12 | WrongType | дескриптор указывает на объект другого типа |
| -13 | PeerClosed | другая сторона исчезла (канал закрыт, Reply выброшен) |
| -14 | TableFull | таблица дескрипторов процесса полна (256) |
| -15 | Timeout | вышло время ожидания |

## Дескрипторы и права

Дескриптор — `u32`: `(поколение << 16) | (слот + 1)`; 0 недействителен. Закрытый слот получает
новое поколение, поэтому старое значение отвергается (`BadHandle`), даже если слот занят снова.
Дескрипторы, выданные ядром до запуска программы, получают значения 1, 2, 3... в порядке выдачи.

Права: `READ`=1 (принять, ждать), `WRITE`=2 (вызвать, отправить, сигналить, ответить, убить),
`DUP`=4 (можно размножить), `TRANSFER`=8 (можно передать в сообщении). У объектов памяти есть
ещё `MAP`=16 (можно отобразить), `EXEC`=32 (можно отобразить исполняемой; пока никакой вызов его
не выдаёт) и `PHYS`=64 (можно узнать физический адрес). Копия может только потерять права.

Объекты: Process, Thread (пока один поток на процесс), Channel, Notification, Reply (право
ответить на один вызов; ядро создаёт его при `call` и выдаёт получателю в `recv`), MemoryRegion,
MmioRegion, Interrupt, IoPortRange и Resource (см. ниже). Объект живёт, пока есть хотя бы один
дескриптор или сообщение в пути. Когда процесс завершается, все его дескрипторы закрываются,
объекты освобождаются, а ожидающие просыпаются.

## Сообщение

160 байт: `tag: u64`, `len: u32` (≤ 128), `nhandles: u32` (≤ 4), `handles: [u32; 4]`,
`data: [u8; 128]`. Дескрипторы в сообщении переносятся: у отправителя они удаляются, и нужно право
`TRANSFER`. У получателя появляются новые значения, а на выходе `handles[]` содержит значения из
таблицы получателя.

`timeout` задаётся в тиках 100 Гц, 0 значит ждать бесконечно. Ожидание не крутит цикл: задача
переходит в состояние Waiting, CPU уходит в HLT, а будит её другая сторона или срок. Когда у
канала не остаётся дескрипторов с `READ`, он закрывается, и все ждущие `call` получают
`PeerClosed`.

## Разделяемая память (этап 2, пункт 12)

MemoryRegion — набор физических страниц, которым владеет объект ядра. `mem_create` создаёт
обычную (анонимную) область. Дескриптор уходит другому процессу в сообщении, обычно копией с
меньшими правами. Каждый процесс отображает область через `mem_map` и видит записи другого.

- `prot` у `mem_map`: `READ`=1, `WRITE`=2, `EXEC`=4. `READ` обязателен; `WRITE|EXEC` вместе
  запрещено (W^X), ответ `InvalidArgument`. Нужные права: `MAP`+`READ`, для записи ещё `WRITE`, для
  исполнения — `EXEC`. По умолчанию страницы неисполняемые (NX), а `EXEC` пока не выдаёт ни один
  вызов, поэтому разделяемая память не бывает исполняемой. Процесс, который пишет через
  отображение только для чтения, получает #PF, и ядро его завершает.
- `hint` зарезервирован (передавайте 0): адрес выбирает ядро в области mmap процесса.
- Отображается вся область; `mem_unmap` принимает ровно адрес, который вернул `mem_map`
  (частичное снятие не поддерживается).
- Отображение держит свою ссылку: закрытие дескриптора его не снимает. Страницы освобождаются,
  когда закрыт последний дескриптор и снято последнее отображение. Завершение процесса закрывает
  его дескрипторы и снимает отображения.
- Удалены: старый механизм SMR (вызовы 120–122, сырые физические адреса без владельца),
  `dma_alloc` (130), отдававший физический адрес в ring 3, прямой ввод-вывод в порты (60/61),
  `irq_wait` (62) и `vfs_register` (100).

DMA: `mem_create_contig(resource, size)` выделяет физически непрерывные страницы, и у дескриптора
есть `PHYS`. `mem_phys` возвращает адрес, который драйвер записывает в устройство. Это может
сделать только процесс с дескриптором Resource вида DMA (с `WRITE`). Копию без `PHYS` можно отдать
клиентам, чтобы они не узнали адрес.

## Оборудование как дескрипторы (этап 2, пункт 13)

Объекты Interrupt, IoPortRange, MmioRegion и Resource нельзя создать системным вызовом. Их создаёт
только привилегированный корень (сейчас это загрузочный код ядра, `core::object::kernel_new_*`, а
потом `seed`) и передаёт драйверу начальными дескрипторами (`core::elf::spawn_with_handles`).

- Interrupt: либо линия ISA IRQ, сейчас только 3, 6 или 8 (их не использует ни один драйвер
  ядра), либо вектор MSI/MSI-X. Одна линия или один вектор — один объект.
  - Линия: при работе через I/O APIC она идёт по переопределениям из MADT на вектор
    0x20 + IRQ. После `irq_bind` каждое прерывание маскирует линию, делает OR `bits` в
    уведомление и будит ждущего. EOI посылает ядро. Драйвер обслуживает устройство и вызывает
    `irq_ack`, который снимает маску. С создания и до первого `irq_ack` линия замаскирована,
    при удалении объекта её снова маскируют.
  - Вектор MSI/MSI-X (вызов 254): вызывающий передаёт дескриптор PciDevice (после
    `pci_claim`, право WRITE). Ядро выделяет `count` векторов, настраивает capability MSI-X
    (предпочтительно) или MSI функции (адрес локального APIC и векторы), включает её и
    возвращает по одному дескриптору Interrupt на вектор, по порядку векторов. Ошибки:
    `NotSupported` (нет ни MSI, ни MSI-X), `Busy` (MSI уже включён, например драйвером
    ядра), `OutOfMemory` (нет свободных векторов, 0x40–0xEF). `irq_bind` работает как для
    линии, но MSI ничего не маскирует: каждое прерывание делает OR `bits` в уведомление, а
    `irq_ack` ничего не делает. Причину драйвер узнаёт из устройства. Когда закрыт последний
    дескриптор вектора (или процесс завершился), вектор освобождается, а с последним
    вектором функции MSI на устройстве выключается.
- IoPortRange: порты `[base, base+count)`. Механизм — карта разрешений ввода-вывода в TSS.
  `IOPL` остаётся 0. `ioport_enable` строит карту процесса (бит на порт, 1 = запрещён), а
  планировщик копирует её в TSS при переключении на этот процесс (только используемые байты и
  только если загружена карта другого процесса). У процессов без портов карта выключена
  (`iopb_offset` за пределом TSS): любой IN/OUT даёт #GP, и процесс завершается. Сам доступ к
  порту ничего не стоит, системного вызова на каждый доступ нет. Как и отображение, включённый
  диапазон держит ссылку и действует до `ioport_disable` или завершения процесса.
- MmioRegion: физический диапазон устройства (например, BAR PCI). `mem_map` работает с ним как с
  MemoryRegion, но страницы отображаются без кэширования (PCD|PWT) и никогда не освобождаются.
  Обычную память, которой управляет аллокатор страниц, нельзя выдать как MMIO.
- Resource: право создавать особые объекты. Вид DMA разрешает `mem_create_contig`.

Тесты: параметр ядра `selftest=mem` (`user/memtest`, `user/uartdrv`). Драйверу COM2 (`uartdrv`)
нужен второй последовательный порт в QEMU: `-serial file:com1.log -serial file:com2.log`.

## Экран, клавиатура, часы (игры и эмуляторы)

Реализация: `core/syscall/screen.rs`; обёртки в `user/liboos/src/screen.rs`. Программе нужна
возможность Framebuf (оболочка выдаёт её каждой запускаемой программе).

| № | Вызов | Аргументы → результат |
|---|---|---|
| 21 | sleep_ms | ms → 0; задача действительно спит (оболочка и другие задачи работают), не меньше `ms`, будится тиком 100 Гц, поэтому опоздание до 10 мс |
| 260 | screen_acquire | info* → 0 |
| 261 | screen_release | → 0 |
| 262 | screen_flush | → 0; вызывающий должен владеть экраном |
| 263 | kbd_mode | raw (0 или 1) → 0 |
| 264 | kbd_event | → событие, 0 если очередь пуста |
| 270 | clock_ns | → монотонное время в наносекундах с загрузки |

screen_acquire: отображает загрузочный фреймбуфер в процесс (чтение и запись, без исполнения, без
кэширования, как отображение MmioRegion) и пишет в `info*` 32 байта: `addr: u64`, `width: u32`,
`height: u32`, `pitch: u32` (байт на строку), `bpp: u32`, `red_shift`, `green_shift`,
`blue_shift` (по байту) и один байт выравнивания. `addr` уже включает смещение внутри первой
страницы. С этого момента консоль ядра продолжает вести текст в теневом буфере, но пикселей не
рисует (`arch/x86_64/framebuffer.rs`, `screen_held`). Экраном владеет один процесс, второй
вызывающий получает -5 (Busy). Без возможности Framebuf вернётся -2, без фреймбуфера -7.
`screen_release` возвращает экран, и консоль перерисовывается из тени. Отображение остаётся до
завершения процесса, но пользоваться им нельзя. Когда владелец завершается или его убили, ядро
само освобождает экран (разбор задачи в планировщике, `screen::process_gone`).

screen_flush: в VMware SVGA II запись во фреймбуфер не видна, пока не послана команда обновления.
Вызов посылает её для всего экрана. Вызывайте его раз за кадр. На обычном фреймбуфере он ничего не
делает.

kbd_mode и kbd_event: в режиме raw программа получает сканкоды PC (набор 1) как события вместо
построчного ввода консоли (`core/stdin.rs`). Значение события: биты 0..7 — сканкод (1..0x7F), бит
8 — у клавиши был префикс 0xE0, бит 9 — отпускание. 0 значит, что событий нет. В raw может быть
один процесс, другой получит -5. Когда владелец завершается, ядро выходит из raw и сбрасывает
очередь. Ctrl+C работает: прерывание клавиатуры ставит флаг прерывания до постановки сканкода в
очередь. Обычно программу убивает оболочка, но программа, которая никогда не блокируется, лишила
бы её процессорного времени. Поэтому ядро само завершает программу, владеющую экраном или
raw-клавиатурой, при её очередном вызове `kbd_event`, `screen_flush` или `sleep_ms` (код выхода
130) и освобождает экран и клавиатуру. Текст, вставленный Ctrl+V, и ввод с последовательного порта
в raw не доставляются.

clock_ns: монотонные часы, по TSC, если он откалиброван (иначе по тику 100 Гц).

## Звук (вывод)

Реализация: `core/syscall/audio.rs` и микшер `drivers/audio/mixer.rs`; обёртка
`user/liboos/src/audio.rs` (`Audio::open`, `write`, `queued`, `drain`); пример `apps/tone`.
Программе нужна возможность Framebuf (та же, что для вызовов экрана).

| № | Вызов | Аргументы → результат |
|---|---|---|
| 271 | audio_open | rate, channels → номер потока (1..4) |
| 272 | audio_write | stream, ptr, bytes → принято байт (не блокирует) |
| 273 | audio_queued | stream → кадров в буфере |
| 274 | audio_close | stream → 0 |
| 275 | audio_volume | stream, percent (0..100) → 0 |

audio_open: `rate` — 48000, 44100 или 22050 Гц, `channels` — 1 или 2. Отсчёты — знаковые
16-битные little endian, каналы чередуются. Ядро пересчитывает частоту под звуковое устройство
(линейная интерполяция) и делает из моно стерео. Ошибки: -2 без возможности Framebuf, -3 для
любого другого формата, -7 если звукового устройства нет (программе стоит продолжить молча), -14
если заняты все 4 потока (на все процессы вместе), -6 если не хватило памяти.

audio_write: копирует целые кадры (`channels * 2` байт) в кольцо потока в ядре на 200 мс
(`rate / 5` кадров). Возвращает число принятых байт, 0 значит, что кольцо полно, и остаток нужно
записать позже. Неполный кадр в конце игнорируется. За один вызов берётся не более 256 КиБ.
Вернётся -11, если `stream` не открытый поток вызывающего, и -10 при плохом указателе.

audio_queued: кадры (в частоте самого потока), которые микшер ещё не забрал. Держите значение
выше примерно 50 мс звука, чтобы не было пропусков. Опрашивайте его вместе с `sleep_ms`, чтобы
задавать темп записи. После выхода из потока кадр ещё до 60 мс лежит в устройстве. Когда значение
равно 0, поток пуст, но чтобы услышать хвост, подождите ещё около 100 мс (`Audio::drain` так и
делает).

audio_volume: усиление потока, по умолчанию 100. Кривая `(percent / 100)^2`. Общая громкость
устройства (команда оболочки `volume`) действует поверх.

Микширование: ядро кормит устройство из таймерного тика звука 100 Гц (`audio::timer_tick`).
Каждый тик оно поддерживает в кольце устройства около 60 мс, суммирует потоки, выше 3/4 шкалы
применяет мягкое колено (как в микшере DOOM) и затем отсекает по 16 битам. Программе достаточно
держать буфер потока заполненным. Пока ни в одном потоке нет данных, ничего не пишется, устройство
молчит, а другие пользователи `audio::submit` (DOOM, `soundtest`) не затронуты. Потоки ring 3 и
DOOM между собой не суммируются: если DOOM держит очередь устройства полной, потоки ждут.

Очистка: поток закрывается по `audio_close`, при завершении или убийстве программы (разбор задачи
в планировщике, `screen::process_gone` вызывает `audio::process_gone`).

Проверка: `apps/tone` играет 440 Гц (моно, 48000 Гц), затем мажорный аккорд до (стерео, 44100 Гц)
и выходит. Запустите QEMU с `-audiodev wav,id=a0,path=out.wav` и `intel-hda`/`hda-duplex`, `AC97`
или `ES1370`, затем проверьте в WAV уровень и частоту.

## Драйверы в ring 3

Реализация: `core/pcidev.rs` (таблица захватов, конфигурационное пространство),
`core/syscall/drv.rs` (обвязка), код объектов в `core/object.rs`; обёртки в `user/libdriver`.
Руководство: [Драйверы в ring 3](dev/drivers.md).

Новый тип объекта 11, `PciDevice`: одна захваченная функция PCI (права READ, WRITE, DUP,
TRANSFER). Новый вид Resource, `PCI` (2): перечисление и захват функций PCI. Создаёт его только
ядро (`devmgr` получает его начальным дескриптором 1).

| № | Вызов | Аргументы → результат |
|---|---|---|

Изменено: `mem_create_contig` (243) принимает третий аргумент `flags` (бит 0: отображать без
кэша) и принимает дескриптор `PciDevice` с WRITE вместо ресурса DMA, так что драйвер выделяет
DMA-память для своего устройства. `irq_alloc_msi` (254) тоже принимает дескриптор `PciDevice`.

Когда закрыт последний дескриптор `PciDevice` (или его владелец завершился), функция
освобождается: управление шиной выключается, владелец снова «свободна». Таблица захватов
помечает функции хранилища, дисплея, звука, мостов и USB как принадлежащие ядру, а также сетевую
карту, которую использует сетевой стек ядра.
