# Драйверы в ring 3

Драйвер может быть пакетом. Он работает как обычный процесс ring 3, получает ровно одну функцию
PCI, и менеджер устройств запускает его, когда пакет установлен. Пересборка ядра для нового
драйвера не нужна.

Состояние сейчас: механизм работает, первый драйвер, `drv-e1000`, перенесён. Остальные драйверы
пока в ядре. Сетевой стек тоже остаётся в ядре; драйвер сетевой карты в ring 3 передаёт ему
пакеты через общее кольцо.

## Из чего это состоит

```
tomato install drv-e1000        кладёт /usr/lib/drivers/e1000/{drv-e1000,driver.conf} в файловую систему
devmgr (ring 3, запускается при загрузке)   сканирует PCI, читает driver.conf, захватывает подходящую
                                            функцию, запускает драйвер, перезапускает при падении
drv-e1000 (ring 3)                          отображает BAR 0, строит DMA-кольца, говорит с сетевым стеком ядра
ядро                                        таблица захватов, объекты PCI, DMA-память, прерывания, кольцо пакетов
```

- `devmgr` (`user/devmgr`) — единственный процесс с ресурсом PCI. Ядро запускает его после
  самотеста загрузки (параметр ядра `devmgr=off` отключает) и устанавливает ту же программу как
  `/usr/bin/devctl`.
- `libdriver` (`user/libdriver`) — библиотека драйвера поверх `liboos`.
- Пакет драйвера — обычный `.tmt` с таблицей `[driver]` в манифесте.

## Манифест драйвера

```toml
name = "drv-e1000"
version = "0.1.0"
description = "Intel e1000 network driver for ring 3"
arch = "x86_64"
depends = []

[[files]]
src = "../target/x86_64-unknown-oos/release/drv-e1000"
dest = "/usr/lib/drivers/e1000/drv-e1000"

[driver]
match = ["pci:8086:100e", "pci:8086:100f", "pci-class:02:00"]
exec = "/usr/lib/drivers/e1000/drv-e1000"      # необязательно: по умолчанию первый файл
```

- Записи `match`: `pci:VVVV:DDDD` (производитель и устройство, hex) или `pci-class:CC:SS`
  (класс и подкласс, hex). Функция подходит, если подошла любая запись.
- Имя драйвера — имя пакета без `drv-` (`e1000`). Все файлы должны лежать в
  `/usr/lib/drivers/<имя>/`.
- `tmt pack` добавляет в пакет `/usr/lib/drivers/<имя>/driver.conf`:

  ```
  name=e1000
  exec=/usr/lib/drivers/e1000/drv-e1000
  match=pci:8086:100e,pci:8086:100f
  ```

  и строку метаданных `driver_match=...`. `tomato` о драйверах ничего не знает: он ставит файлы,
  а `devmgr` находит `driver.conf`. Старые пакеты и старый `tomato` остаются совместимыми.
  `tomato remove` удаляет файлы. Работающий драйвер продолжает работать, пока не завершится.
- `devmgr` смотрит в `/usr/lib/drivers` раз в секунду, так что драйвер стартует вскоре после
  `tomato install`.

## devctl

```
devctl list                список функций PCI: владелец (kernel, ring3, free), драйвер, состояние, pid, перезапуски
devctl start <драйвер>     запустить остановленный драйвер
devctl stop <драйвер>      завершить и не перезапускать
devctl restart <драйвер>   завершить и запустить снова
```

`devctl` говорит с `devmgr` через два файла: `devmgr` пишет `/run/devmgr.status`, а `devctl`
дописывает команды в `/run/devmgr.cmd`. Строки журнала драйвера видны в `dmesg` (и на
последовательном порту) с именем драйвера.

Драйвер, который завершился, запускается снова через 1 с; задержка удваивается до 30 с.
Драйвер, проработавший 15 с и больше, начинает с 1 с. Устройство, которым управляет само ядро
(используемая сетевая карта), забирается у ядра только если установлен подходящий пакет
драйвера: `devmgr` захватывает его с флагом принуждения, ядро сбрасывает устройство, и его
собственный драйвер останавливается. Ядро сохраняет настройки IP, поэтому новый драйвер
продолжает с той же арендой. Без пакета ничего не меняется: работает драйвер в ядре.

## Сторона ядра

Объекты и вызовы описаны в [ABI системных вызовов](../syscall-abi.md), «Драйверы в ring 3».
Коротко:

- `Resource(PCI)` позволяет процессу перечислять функции PCI (`pci_enum`) и захватывать одну
  (`pci_claim`). Он есть только у `devmgr`.
- Захват возвращает дескриптор `PciDevice`. Таблица захватов держит одного владельца на
  функцию: ядро или ring 3. Когда последний дескриптор исчезает, функция снова свободна
  (управление шиной выключено).
- Из дескриптора `PciDevice` драйвер получает всё, что ему можно трогать: `pci_open` даёт BAR
  как `MmioRegion` или `IoPortRange`, либо прерывание INTx; `irq_alloc_msi` даёт векторы
  MSI/MSI-X; `pci_cfg_read` и `pci_cfg_write` работают с конфигурационным пространством только
  этой функции (не с идентификаторами, BAR, базой ROM); `mem_create_contig` на этом дескрипторе
  выдаёт DMA-память с физическим адресом, при желании без кэша.
- Линия INTx отклоняется, если её делит драйвер ядра другой функции.
- IOMMU пока нет. Драйвер с управлением шиной может писать DMA куда угодно. Кольца, права и
  таблица захватов защищают от ошибок, но не от враждебного драйвера.

## libdriver

```rust
let d = Driver::new("mydrv");          // задаёт тег журнала, берёт дескриптор 1 (устройство) и 2 (devmgr)
let pci = d.pci();
pci.enable_bus_master()?;              // память, порты, управление шиной; запрет INTx снят
let regs = pci.bar_map(0)?;            // Mapping без кэша: regs.read::<u32>(off), regs.write(off, v)
let ports = pci.bar_io(1)?;            // IoPorts; сначала .enable()
let irq = pci.irq()?;                  // MSI, если есть, иначе INTx; Irq { wait, ack, unmask }
let dma = pci.dma_alloc(64 * 1024, false)?;   // Dma { virt(), phys(), len(), as_ptr(), map, region }
pci.config_read(0x3C, 1)?; pci.config_write(0x04, 2, v)?;
libdriver::log!("link {}", up);        // serial + журнал событий ядра (dmesg), тег [mydrv]
d.ready("текст состояния");            // сообщает devmgr, что драйвер работает
```

- `Irq::wait(ticks)` возвращает биты уведомления, 0 при таймауте. Бит 1 (`IRQ_BIT`) — прерывание
  устройства. После обработки вызовите `ack()`: он снимает маску с линии.
  `Driver::run(&irq, ticks, f)` — цикл вокруг этого.
- `Irq::notification()` — само уведомление; другие стороны могут выставлять другие биты
  (сетевой стек ядра использует бит 2).
- Для памяти устройства и памяти, общей с другим процессом, используйте
  `liboos::mem::Mapping::read` и `write` (volatile).
- Вместо `liboos::entry!` пишите `libdriver::driver_entry!("имя", main)`. Драйверу нельзя
  использовать `println!`: стандартный вывод процесса ring 3 попадает и в оболочку. Используйте
  `log!`.

## Первый драйвер: пример e1000

Код: `apps/drivers/e1000/src/main.rs`. Что он делает:

1. `Driver::new("e1000")`, `pci.info()`, `enable_bus_master()`.
2. `pci.bar_map(0)`: окно регистров (BAR 0 у 8254x — память).
3. `pci.dma_alloc(...)`: один непрерывный регион хранит кольца дескрипторов и буферы пакетов.
   Карта получает физические адреса из `dma.phys()`.
4. Сброс (`CTRL.RST`, ожидание), включение линка, чтение MAC из EEPROM, настройка колец RX и TX,
   включение `RCTL` и `TCTL`.
5. `pci.irq()`. Если не вышло, драйвер опрашивает карту каждый тик.
6. Заполняет заголовок кольца и вызывает `netring::attach(...)`, затем `d.ready(...)`.
7. Цикл: `irq.wait(1)`, чтение `ICR`, публикация готовых дескрипторов RX, возврат освобождённых
   слотов (`RDT`), постановка новых кадров TX (`TDT`), уборка отправленных, слежение за линком.

Сборка пакета:

```
cd apps
cargo +nightly build --release -p drv-e1000        # в Windows: +nightly-x86_64-pc-windows-gnu
..\tools\tmt\bin\tmt pack pkg\drv-e1000.toml -o dist
```

или `apps\build.ps1 -Only drv-e1000`. Чтобы добавить новый крейт, положите его в
`apps/drivers/<имя>`, добавьте в `members` файла `apps/Cargo.toml`, подключите `liboos` и
`libdriver` и напишите `apps/pkg/drv-<имя>.toml`.

## Сетевые драйверы

Сетевой стек ядра пока не сервер, поэтому драйвер карты не реализует сокеты. Он заполняет один
DMA-регион, который одновременно служит памятью пакетов (`net/ext.rs`, `libdriver::netring`):

```
страница 0  заголовок: magic, version, MAC, flags (бит 0 линк, бит 1 работает), nslots, slot_size,
            rx_off, tx_off, rx_prod, rx_cons, tx_prod, tx_cons, rx_len[], tx_len[]
rx_off      nslots слотов приёма: карта пишет кадры сюда, стек читает их на месте
tx_off      nslots слотов передачи: стек копирует кадр, карта отправляет отсюда
```

Индексы — свободно бегущие счётчики `u32` (слот = индекс % nslots). Драйвер владеет `rx_prod` и
`tx_cons`, ядро — `rx_cons` и `tx_prod`. `netring::attach` регистрирует регион и уведомление;
ядро выставляет в нём бит 2, когда кадр ждёт отправки (оно будит драйвер только когда не
удерживает блокировок, поэтому драйвер должен просыпаться и по таймауту). Опубликовав кадры,
драйвер вызывает `netring::poll()`, и стек обрабатывает их в этом вызове. Приём идёт без
копирования; при передаче одно копирование (буфер стека в слот).

Если процесс драйвера умер, стек замечает это при следующей отправке или приёме и сообщает
«нет линка», пока драйвер не подключится снова.

Ограничения: сетевой стек ядра уже должен работать (его поднял драйвер сетевой карты в ядре),
поэтому карта без драйвера в ядре пока не подойдёт. Одна внешняя карта за раз.

## Проверка

QEMU с `-device e1000`, ISO собран `scripts/mkiso.sh` (см. [Тестирование](testing.md)):

```
curl -o /run/drv.tmt http://10.0.2.2:8000/drv-e1000-0.1.0.tmt     # раздаётся python -m http.server
tomato install /run/drv.tmt
ping 10.0.2.2                    # теперь идёт через драйвер в ring 3
devctl list                      # 00:03.0 8086:100e 02:00 ring3 e1000 running
kill <pid drv-e1000>             # devmgr запускает его снова, ping снова работает
dmesg                            # строки [e1000] ... [devmgr] ...
```

В последовательном журнале видна строка `[NET] external NIC driver attached (ring 3)`.

## Что не сделано

- Остальные драйверы (хранилище, звук, USB, другие сетевые карты) всё ещё в ядре.
- Нет IOMMU: драйверу ring 3 с управлением шиной доверяют не настраивать DMA плохо.
- После `devctl stop` устройство остаётся неактивным; вернуть его драйверу ядра без перезагрузки
  нельзя.
- Сетевой стек в ядре; сокеты через IPC — задача на будущее.
