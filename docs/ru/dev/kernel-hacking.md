# Работа с ядром

Как устроен репозиторий и как добавить в ядро три самые частые вещи: команду оболочки, системный
вызов и драйвер. Код в этих местах работает в ring 0. Сначала прочитайте
[Архитектуру](../architecture.md) и [Внутреннее устройство ядра](../../en/kernel.md) (на
английском).

## Карта кода

Ядро — один крейт, `ospab_os`. `src/lib.rs` — корень библиотеки, он подключает каталоги верхнего
уровня строками вида `#[path = "../arch/mod.rs"]`; `src/main.rs` — бинарник с последовательностью
загрузки. В `Cargo.toml` нет разделов `[[bin]]` и `[lib]`.

| Путь | Что там |
|---|---|
| `src/main.rs` | `_start`, последовательность загрузки, `boot_log!` и самопроверки при загрузке |
| `src/lib.rs` | список модулей библиотечного крейта |
| `src/terminal.rs` | консоль: ввод, `help`, команды, не входящие в coreutils, диспетчеризация команд |
| `src/userspace/plum/` | оболочка: разбор, подстановки, встроенные команды (`builtins.rs`), запуск программ (`exec.rs`), стандартный вывод и ввод (`io.rs`), учётные записи |
| `src/userspace/axon/` | coreutils и утилиты: `ls`, `grep`, `ping`, `curl`, `ps`, дисковые утилиты, рабочий стол (`desktop/`) |
| `src/userspace/mod.rs` | подключает `net/`, `drivers/`, `vfs/` и `userland/*` через `#[path]` |
| `src/installer.rs`, `src/installer/` | установщик на диск |
| `src/pci.rs`, `src/acpi/`, `src/xhci/` | доступ к PCI и перечисление, ACPI, USB (xHCI, HID) |
| `src/time.rs`, `src/klog.rs`, `src/esp.rs`, `src/doom.rs` | часы, журнал событий ядра, доступ к ESP для обновления системы, обвязка DOOM |
| `arch/x86_64/` | GDT/TSS, IDT и диспетчер прерываний, PIC/APIC, TSC, клавиатура, мышь, последовательный порт, кадровый буфер и консоль, экран паники. В `boot/` лежит контракт `BootInfo` с загрузчиком |
| `core/` | `scheduler/`, `syscall/` (`mod.rs` с таблицей, `objects.rs`, `screen.rs`, `audio.rs`), `object.rs` (дескрипторы и объекты), `elf.rs`, `fd.rs`, `stdin.rs`, `sync.rs`, `selftest.rs`. `capability/` и `ipc/` — старый код |
| `mm/` | `physical/` (страницы), `virtual/` (таблицы страниц), `heap.rs`, `numa/`, `usercopy.rs` |
| `vfs/` | `mod.rs` (точки монтирования, вызовы дескрипторов), `ramfs.rs`, `cow.rs`, `procfs.rs`, `aeternafs.rs`, `disk_sync.rs`, `persist.rs` |
| `drivers/` | хранилища (`ata`, `ahci`, `nvme`, `virtio_blk`, `gpt`, `block`), `audio/`, `gpu/` (VMware SVGA, VMMouse, буфер обмена хоста), `registry.rs` |
| `net/` | драйверы сетевых карт, Ethernet, ARP, IPv4, ICMP, UDP, TCP, DHCP, DNS, SNTP, `tls/`, `ostp/` |
| `userland/` | `grape` (редактор), `tomato` (пакеты), `seed` (таблица служб); компилируются в ядро |
| `fs/aeternafs/` | AeternaFS v2 как самостоятельный крейт `no_std` с тестами на хосте |
| `gui/` | `oos-ui`, набор виджетов и сессия рабочего стола |
| `user/` | отдельная рабочая область для ring 3: `liboos` и тестовые программы для загрузки |
| `apps/` | отдельная рабочая область для программ и пакетов ring 3; SDK |
| `boot/` | ospab-boot: `common/` (общее), `uefi/`, `bios/`, `ospab.cfg` |
| `tools/` | утилиты для хоста: `tmt/`, `oosfs/`, `mkimage.rs` |
| `scripts/` | `mkiso.sh`, `bios-image.sh`, `run-qemu.*`, `smoke-test.ps1` |
| `doom_engine/` | исходники doomgeneric на C и небольшая libc; собирается `doom_engine/build_doom.sh` |
| `build.rs`, `linker.ld`, `x86_64-ospab.json` | идентификатор сборки, скрипт компоновки ядра, цель ядра |

Не каждый файл `.rs` в `src/` компилируется. `src/main.rs` объявляет `terminal`, `version` и
`installer`; остальное объявляет библиотека. Файлы вроде `src/shell.rs`, `src/ui.rs`,
`src/console.rs` и `src/logger.rs` не входят ни в одно дерево модулей. Если при правке файла
ничего не меняется, проверьте, что какая-то строка `mod` его подключает.

## Добавить модуль или файл

- Новый файл в существующем каталоге: создайте его и добавьте `pub mod имя;` в `mod.rs` этого
  каталога (или `mod имя;`, если он приватный).
- Новый каталог верхнего уровня: добавьте `#[path = "../dir/mod.rs"] pub mod dir;` в
  `src/lib.rs`, как для `arch`, `mm` и `core`.
- Новый внешний крейт: добавьте его в `Cargo.toml`. Он должен быть `no_std`. Ставьте
  `default-features = false`.
- Новый файл C для DOOM: `doom_engine/build_doom.sh` и `build.rs`.
- Каждый исходный файл начинается с лицензионного заголовка. См. [Как внести
  изменения](../../../CONTRIBUTIONS_ru.md).
- Собирайте командой `./build.sh kernel`: это быстрая проверка компиляции. См.
  [Тестирование](testing.md).

## Добавить команду оболочки

Куда её класть, зависит от того, должна ли она работать в конвейерах и перенаправлениях.

**Команда в стиле coreutils (предпочтительно).** Читает аргументы, пишет в вывод оболочки,
работает в конвейерах и с `>`.

1. В `src/userspace/axon/mod.rs` напишите `fn cmd_foo(args: &[String])`. Печатайте
   вспомогательными функциями из начала файла: `out(&str)`, `err(&str)`, `outc(&str, цвет)`.
   Они идут через `plum::io`, на этом держатся перенаправления и конвейеры. Короткий образец —
   `cmd_basename`. Большая команда может лежать в своём файле (`src/userspace/axon/foo.rs` с
   `pub mod foo;` и `pub fn run(args: &str)`, как `ping.rs` или `clip.rs`).
2. Добавьте `"foo" => cmd_foo(args),` в `match name` в `axon::run`. Для формы
   `pub fn run(&str)` вызывайте с `&joined()`.
3. Добавьте `"foo"` в `command_list()` в том же файле. По нему работают дополнение по Tab и
   `type`.
4. Добавьте строку в таблицу `HELP` в `src/terminal.rs` и, если хотите, чтобы `help foo`
   говорила больше, ветку в `help_detail`.
5. Добавьте команду в список в `docs/en/shell.md` и в перевод [Оболочка и утилиты](../shell.md).

**Команда консоли.** Команды, которые рисуют полноэкранный интерфейс, работают с консолью
кадрового буфера напрямую или управляют машиной (`grape`, `reboot`, `date`, `tomato`), лежат в
`src/terminal.rs`. Их нельзя ставить в конвейер или перенаправлять.

1. Напишите `fn cmd_foo(args: &str)` в `src/terminal.rs`.
2. Добавьте имя в `TERMINAL_COMMANDS` и ветку в `dispatch_console`.
3. Если команда занимает экран или ждёт клавиш, добавьте её в `NO_PAGER`, чтобы постраничный
   вывод не мешал.
4. Добавьте имя в `CONSOLE_COMMANDS` в `src/userspace/plum/mod.rs`, чтобы оболочка находила его,
   когда оно встречается в скрипте. Если такую команду поставить в конвейер, оболочка выдаст
   замечание.
5. `HELP` и `help_detail`, как выше.

**Встроенная команда оболочки** (меняет состояние самой оболочки, как `cd` или `export`):
добавьте её в `src/userspace/plum/builtins.rs` (`builtins::run`).

Перед тем как добавлять команду в ядро, спросите себя, нельзя ли сделать её программой ring 3
([Первая программа](first-program.md)). В ядре должны быть только команды, которым нужны
внутренности ядра.

## Добавить системный вызов

Сначала прочитайте [Системные вызовы](../syscall-abi.md). Для диспетчеризации значима только
таблица в `core/syscall/mod.rs` (`DISPATCH_TABLE`). Перечисление `SyscallNumber` над ней — это
список имён, для диспетчеризации оно не используется (в нём до сих пор есть вызовы, которых нет в
таблице, например `IpcSend = 10` и `Fork = 30`).

Занятые номера:

| Диапазон | Вызовы |
|---|---|
| 0–5 | exit, write, read, open, close, seek |
| 20–24 | yield, sleep_ms, getpid, spawn, preempt_control |
| 32 | waitpid |
| 40, 41 | mmap, munmap |
| 50–52 | sysinfo, uptime, get_tasks |
| 70, 80, 110 | cap_delegate, med_assign, dev_detach |
| 200–253 | дескрипторы, каналы, уведомления, процессы, регионы памяти, прерывания, порты |
| 260–264, 270 | экран, сырая клавиатура, часы |
| 271–275 | звук |

Шаги:

1. **Выберите номер.** Продолжите семейство (например, 276 для звука или часов) или начните новый
   блок из десяти с 280. Запишите его в `docs/en/syscall-abi.md`.
2. **Напишите обработчик.** Положите его в файл в `core/syscall/` (добавьте `pub mod foo;` в
   `core/syscall/mod.rs`) или рядом с похожими вызовами. Образец — `core/syscall/audio.rs`.
   Сигнатура — `pub fn name(a1: u64, a2: u64, ...) -> i64`. Результат — значение >= 0 или
   отрицательный `SyscallError`, например `E::InvalidArgument as i64`.
3. **Сначала проверьте привилегию.** У процесса есть список значений `Capability`
   (`core/scheduler/mod.rs`: FsRead, FsWrite, Framebuf, Serial, Net, Spawn, System, Device, ...).
   Используйте `scheduler::has_capability(Capability::X)`; процесс с `System` проходит любую
   проверку. Программы из оболочки получают Serial, FsRead, FsWrite и Framebuf (`run_elf` в
   `src/userspace/plum/exec.rs`). Экран, сырая клавиатура и звук проверяют Framebuf. Не раздавайте
   каждой программе новую возможность без причины. Если это новый вид возможности, добавьте
   значение `Capability` и выдавайте его в `run_elf` только когда оно задумано как общее. Вызовы
   над объектами ядра привилегий не требуют: разрешением служат дескриптор и его права
   (`core/object.rs`).
4. **Не доверяйте указателю.** Пользуйтесь `crate::mm::usercopy`: `range_ok(addr, len)`,
   `copy_from_user(dst, src)`, `copy_to_user(dst, src)`, `read_user_bytes(src, len, max)`,
   `read_user_str(src, len, max)`. Ошибку преобразует `SyscallError::from(UserCopyError)`.
   Ограничивайте размеры (`MAX_IO_CHUNK` — 64 КиБ) и не выделяйте память по непроверенной длине.
5. **Блокировка.** Вызов может спать: у каждой задачи свой стек ядра. Используйте
   `scheduler::park(deadline)` в цикле, как `screen::sleep_ms`. Никогда не блокируйтесь, удерживая
   блокировку. Если вызовом пользуются программы, владеющие экраном или клавиатурой, вызывайте
   `check_interrupt()`, чтобы работал Ctrl+C.
6. **Уборка.** Если вызов выдаёт то, что нужно вернуть при смерти процесса, освободите это в
   пути разбора. Образец — `screen::process_gone`, его вызывает планировщик (звуковые потоки,
   экран, сырая клавиатура).
7. **Зарегистрируйте.** Добавьте `(NNN, |a| foo::name(a.arg1, a.arg2, a.arg3)),` в
   `DISPATCH_TABLE`. Таблица просматривается линейно. Отсутствующий номер возвращает -1.
8. **liboos.** Добавьте `pub const NAME: u64 = NNN;` в `sys::nr` в `user/liboos/src/sys.rs` (в
   файле сказано, что номера должны совпадать с ядром) и безопасную обёртку в подходящий модуль на
   основе `sys::syscall0`..`syscall3`. Форм на четыре и пять аргументов пока нет; добавьте их в
   `sys.rs`, если нужно. Для API в стиле объектов возвращайте `Result<_, ipc::Error>`, как `mem`,
   или сырой `i64`, как `screen`. В одном модуле держитесь одного стиля.
9. **Документация.** Добавьте строку и абзац в `docs/en/syscall-abi.md`, обёртку — в
   [справочник liboos](liboos.md), и переведите оба в `docs/ru`.
10. **Тест.** Напишите небольшую программу ring 3. Либо положите её в `apps/` (как `gfxtest` или
    `tone`: пакет, который сможет запустить любой), либо в `user/` и вызовите из самопроверки при
    загрузке в `src/main.rs`, чтобы регрессии были видны в журнале загрузки. Проверьте пути
    ошибок: плохой указатель, неверный дескриптор, нет привилегии.

## Добавить драйвер

Сегодня драйверы работают в ring 0. Лучше всего начинать с драйвера для оборудования, которое
есть в VMware или QEMU: его можно проверить.

1. **Файл.** Создайте `drivers/<имя>.rs` (или в `drivers/audio/`, `drivers/gpu/`; сетевая карта
   идёт в `net/`) и объявите его в `mod.rs` родителя.
2. **Найдите устройство.** `ospab_os::pci` (`src/pci.rs`) хранит таблицу PCI, заполняемую при
   загрузке:

   ```rust
   crate::pci::find_by_vendor_device(vid, did)        // Option<&PciDevice>
   crate::pci::find_by_class(class, subclass, progif)
   crate::pci::read_bar(bus, dev, func, bar_index)    // BarType::Io { .. } или BAR памяти
   crate::pci::enable_bus_master(bus, dev, func)
   crate::pci::config_read32(bus, dev, func, offset)  // и формы на 8, 16 бит и записи
   crate::pci::find_capability(bus, dev, func, cap_id)
   ```

   `probe` должен быть дешёвым: читайте только конфигурационное пространство PCI.
3. **Инициализация.** Сделайте `pub fn init() -> bool` (или `probe_and_init`). Возвращайте
   `false`, если устройства нет или оно не работает. Не паникуйте, если оборудования нет.
   Отображайте MMIO через HHDM или помощники таблиц страниц в `mm/virtual`; включайте
   bus mastering до DMA; буферы DMA должны быть физически непрерывными и лежать ниже предела,
   который поддерживает устройство.
4. **Пишите в журнал с тегом.** Строки подробностей пишите в последовательный порт с тегом в
   квадратных скобках и `\r\n`:

   ```rust
   serial::write_str("[FOO] Found 1234:5678 at 00:03.0\r\n");
   ```

   Существующие драйверы используют `[ES1371]`, `[AUDIO]`, `[NET]`, `[e1000]` и так далее. Пишите,
   почему устройство отвергнуто. Строка, начинающаяся с `[ FAIL ]`, проваливает автотест, поэтому
   не начинайте так отладочные строки.
5. **Подключите к загрузке.** В `src/main.rs` вызовите `boot_step("Foo")` и оберните
   инициализацию в `ospab_os::drivers::registry::try_init_driver("Foo", || { ... })`, который
   пишет `[DRV] Foo: probing / active / not available` и запоминает результат. Затем выведите
   ровно одну строку состояния:

   ```rust
   boot_log!(Status::Ok, "Foo", "{} at {}", model, detail);       // [  OK  ]
   boot_log!(Status::Absent, "Foo", "no controller");             // [  --  ] необязательного устройства нет
   boot_log!(Status::Warn, "Foo", "...");                         // [ WARN ]
   boot_log!(Status::Fail, "Foo", "...");                         // [ FAIL ] только для настоящих ошибок
   ```

   `Absent` — правильное состояние для устройства, которого может не быть. `Fail` — для
   устройства, которое есть, но не работает; оно же проваливает автотест и пишется в журнал
   событий ядра. `Status::Info` — для фактов. Строка — не более 160 байтов. Короткие образцы:
   `GPU`, `Audio` и `USB` в `src/main.rs`.
6. **Прерывания.** Линии старого PIC разбирает `match irq` в `irq_dispatch`
   (`arch/x86_64/idt.rs`). Линии сетевых карт 9, 10 и 11 вызывают
   `userspace::net::handle_net_irq`. Обработчик прерывания может брать только те блокировки,
   которые безопасны в контексте прерывания (`IrqSpinLock`). Многие драйверы вместо этого
   опрашивают устройство; это допустимо, если драйвер это сообщает. Соблюдайте [правила
   блокировок](../../en/kernel.md#locks).
7. **У сетевой карты** в `net/mod.rs` больше мест, которые нужно тронуть: константа `NIC_*`, цепочка
   проб в `init` и ветки, которые читают MAC, отправляют, принимают, определяют состояние линии,
   прерывание и названия. Найдите все по `NIC_PCNET`.
8. **Диск** должен попасть в таблицу в `drivers/mod.rs` (`DiskKind`, `init`). Всё адресуется
   секторами по 512 байтов.
9. **Список оборудования и документация.** Добавьте устройство в `docs/en/hardware.md` и в
   перевод [Оборудование](../hardware.md).
10. **Проверка** в QEMU с подходящим `-device` (см. [Тестирование](testing.md)) и, для всего, что
    бывает у гостя VMware, в VMware. Смотрите последовательный журнал.

В `drivers/registry.rs` и `drivers/driver_trait.rs` написано, что паника драйвера перехватывается.
Это не так: ядро собрано с `panic = "abort"`, и паника в `init` останавливает машину. Реестр лишь
запоминает, вернул ли `init` истину.

## Блокировки

Пользуйтесь примитивами из `core/sync.rs` и соблюдайте ранги из [внутреннего устройства
ядра](../../en/kernel.md). Коротко: `IrqSpinLock` для данных, общих с обработчиками прерываний,
`Mutex` для долгих секций в контексте задачи, никакого ввода-вывода, ожидания и `park` под
спин-блокировкой, блокировки берутся в порядке возрастания ранга, HEAP последним. Если добавляете
блокировку, выбирайте ранг по тому, что она вызывает под собой, и добавьте строку в таблицу в
`docs/en/kernel.md`. В новом коде не используйте `static mut` для общего состояния.

## Куда смотреть, когда что-то сломалось

- Сначала последовательный журнал. `[CRITICAL] Process N name at 0x...` — сбой процесса ring 3;
  `[FATAL] CPU Exception` с `Fault RIP` — сбой ядра. Сопоставьте адрес с выводом `objdump -d` (или
  `nm`) для `target/x86_64-ospab/release/ospab_os`. `build.sh` убирает отладочную информацию, но
  оставляет символы.
- `dmesg` в оболочке показывает журнал событий ядра.
- Загрузитесь с пункта загрузчика «ospab.os (debug)»: `debug=1` выводит подробные строки на экран,
  `selftest=ipc` запускает проверки IPC, `persist=ro` запрещает запись сохранённого слоя.
  Параметры: `debug=1`, `persist=ro`, `selftest=ipc|mem|sched|all`, `session=desktop`, `mode=`.
- `testmode` показывает экраны паники и сбоя, не роняя систему.
