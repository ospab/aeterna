# Участие в разработке ospab.os

Здесь описаны порядок отправки патчей, соглашения по коду, лицензия, отчёты об ошибках и правила
для ИИ-агентов. О том, как писать программы и драйверы, см. [руководство
разработчика](docs/ru/dev/README.md); команды сборки и тестов — в [Сборке](docs/ru/building.md)
и [Тестировании](docs/ru/dev/testing.md).

---

## Начало работы

### Требования

| Инструмент | Назначение |
|---|---|
| Rust nightly с `rust-src` | Ядро, загрузчики, программы ring 3 (`build-std`, JSON-цели) |
| Rust stable | Хост-утилиты (`tools/tmt`, `tools/oosfs`) и тесты на хосте |
| `xorriso`, `mtools`, `mkfs.vfat` | Гибридный ISO. На Windows их даёт WSL |
| QEMU | Тестирование. Основная целевая платформа — VMware Workstation |
| `dd`, компилятор Си в WSL/Linux | Образ BIOS-загрузчика, DOOM (необязательно) |

На Windows без Visual C++ Build Tools берите GNU-набор (`nightly-x86_64-pc-windows-gnu`). Ядро
собирается под свою цель `x86_64-ospab.json`; cargo берёт её из `.cargo/config.toml`, а
`rustup target add` не нужен.

### Клонирование и сборка

```bash
git clone https://github.com/ospab/aeterna.git
cd aeterna
git submodule update --init      # doom_engine
./build.sh kernel                # быстрая проверка компиляции
./build.sh                       # ISO: isos/ospab-os-v2-N.iso (в WSL/Linux)
```

`./build.sh image` делает образ диска GPT без WSL. Подробности: [Сборка](docs/ru/building.md).

### Запуск

```bash
qemu-system-x86_64 -m 512M -cpu max -cdrom isos/ospab-os-v2-N.iso -serial stdio
```

`N` — номер вашей сборки (`ls isos`). Больше устройств (диск, сеть, звук, UEFI): скрипты
`scripts/run-qemu.ps1` и `scripts/run-qemu.sh` и командные строки в
[Тестировании](docs/ru/dev/testing.md).

## Структура кода

Полная карта — в [Работе с ядром](docs/ru/dev/kernel-hacking.md). Коротко:

| Путь | Описание |
|---|---|
| `src/main.rs` | `_start`, последовательность загрузки, журнал загрузки, самопроверки |
| `src/lib.rs` | корень библиотеки, объявления модулей |
| `src/terminal.rs` | консоль и её команды |
| `src/userspace/plum/` | оболочка |
| `src/userspace/axon/` | coreutils и утилиты |
| `src/installer.rs`, `src/installer/` | установщик на диск |
| `src/pci.rs`, `src/acpi/`, `src/xhci/` | PCI, ACPI, USB |
| `arch/x86_64/` | GDT, IDT, PIC/APIC, клавиатура, кадровый буфер, serial, panic |
| `core/` | планировщик, системные вызовы, объекты и дескрипторы, загрузчик ELF, блокировки |
| `mm/` | физическая память, таблицы страниц, куча, копирование из пользовательской памяти |
| `vfs/` | виртуальная файловая система, RamFS, наложение слоёв, `/proc`, сохранение |
| `drivers/` | хранилища, звук, GPU, реестр драйверов |
| `net/` | драйверы и стек сети, TLS, OSTP |
| `userland/grape/`, `userland/tomato/`, `userland/seed/` | редактор, менеджер пакетов, таблица служб |
| `fs/aeternafs/` | крейт файловой системы AeternaFS v2 |
| `gui/` | библиотека `oos-ui` |
| `user/` | `liboos` и тестовые программы ring 3 |
| `apps/` | программы и пакеты ring 3 (SDK) |
| `boot/` | загрузчик ospab-boot (BIOS, UEFI) |
| `tools/` | хост-утилиты: `tmt`, `oosfs`, `mkimage.rs` |
| `doom_engine/` | doomgeneric (подмодуль git) |

## Соглашения по коду

### Rust

- `#![no_std]` в ядре, `liboos` и ядрах игр. Для `Vec`, `String` и `BTreeMap` подключайте
  `extern crate alloc`.
- У каждой публичной функции и типа есть doc-комментарий (`///`).
- У каждого блока `unsafe` есть комментарий `// SAFETY:` с инвариантом, на который он опирается.
- Для внутренних путей пишите `crate::`.
- В новом коде не используйте `static mut` для общего состояния; следуйте [правилам
  блокировок](docs/en/kernel.md) (на английском). Не паникуйте на плохом вводе из ring 3 или от
  оборудования.
- Драйвер, не нашедший своё устройство, возвращает `false`.

### Именование

| Элемент | Стиль | Пример |
|---|---|---|
| Модули, функции, переменные | `snake_case` | `init_driver`, `send_packet` |
| Типы, трейты, перечисления | `PascalCase` | `PacketBuffer`, `NetDriver` |
| Константы | `SCREAMING_SNAKE_CASE` | `MAX_PACKET_SIZE` |
| Файлы | `snake_case.rs` | `rtl8139.rs`, `ramfs.rs` |

### Организация файлов

- У каждой подсистемы свой каталог с `mod.rs`. Определения трейтов можно держать в `trait.rs`.
- Новый файл должен быть подключён строкой `mod`, иначе он не компилируется.
- Программы ring 3 лежат в `apps/<имя>/`; оболочка и coreutils — в `src/userspace/`.
- Код, зависящий от архитектуры, лежит в `arch/x86_64/`.

### Логирование

- Сообщения подсистем начинаются с тега в квадратных скобках: `[NET]`, `[AHCI]`, `[AUDIO]`.
- Сообщения в serial заканчиваются на `\r\n`.
- Драйвер сообщает итог одной строкой состояния загрузки (`boot_log!` в `src/main.rs`): `Ok`,
  `Warn`, `Fail`, `Absent` (необязательного оборудования нет), `Info`.
- Записи журнала событий ядра идут через `klog` и видны в `dmesg`.
- Отладочные трассировки убирайте до отправки изменения.

### Заголовки лицензии

Проект распространяется под **AGPL-3.0-only** ([LICENSE](LICENSE)). Каждый исходный файл
начинается с:

```rust
// SPDX-License-Identifier: AGPL-3.0-only
// Copyright (c) 2026 Your Name
```

Файлы ядра используют блочную форму (`/* SPDX-License-Identifier: AGPL-3.0-only ... */`). В новых
крейтах в `Cargo.toml` ставьте `license = "AGPL-3.0-only"`.

## Чужой код и файлы

- Используйте код, только если его лицензия совместима с AGPL-3.0-only и вы можете назвать
  источник. Сохраняйте его уведомление и текст лицензии и держите его в отдельном каталоге
  (`doom_engine/` — подмодуль git со своей лицензией GPL-2.0).
- Чужих двоичных файлов в репозитории быть не должно: ROM, образы дисков, данные игр (`*.rom`,
  `*.ssd`, `*.wad`), прошивки, наборы тестов 6502. `.gitignore` их уже исключает, как и `*.tmt`,
  `dist/`, `isos/` и `target/`. Программы просят такие файлы у пользователя; тесты читают их из
  переменных окружения.
- Не коммитьте образы ISO, журналы и дампы падений компилятора (`rustc-ice-*.txt`).
- Никогда не коммитьте и не печатайте ключи подписи. Ключ подписи пакетов
  `%USERPROFILE%\.ospab\tmt.key` принадлежит мейнтейнерам; для проверок берите свои ключи.

## Где нужна помощь

План — в [ROADMAP.md](ROADMAP.md). Главная работа — этап 3: выносить службы из ring 0 по одной.

- Службы в ring 3: `seed`, консоль, хранилище, сеть, звук как отдельные процессы.
- Пробелы в API ring 3 ([справочник liboos](docs/ru/dev/liboos.md), «Чего пока нет»): чтение
  каталога, `stat`, `mkdir`, `unlink`, окружение, запуск программ, ввод мыши.
- Известная ошибка: `open` с флагом 2 (чтение и запись) даёт дескриптор только для чтения.
- Драйверы: USB помимо xHCI, больше сетевых карт и аудиокодеков.
- Тесты на хосте для другого `no_std`-кода, тесты оболочки и VFS.
- Документация: недостающие русские страницы (`drift`, `olang`, `kernel`), сверка руководств с
  исходниками.

## Порядок работы

1. **Ветка** от `master`. Одна ветка — одна тема.
2. **Разработка и проверка.** Команды — в [Тестировании](docs/ru/dev/testing.md).
   - `./build.sh kernel` проходит при любом изменении ядра; тесты на хосте проходят для
     затронутого крейта (`beeb-core`, `drift-core`, `aeternafs`).
   - Загрузите сборку в QEMU, а если трогали загрузку, дисплей, ввод или звук — и в VMware.
     В serial-журнале ищите `[ FAIL ]`, `[CRITICAL]` и `[FATAL]`.
   - Сборка ядра идёт с отключёнными предупреждениями, поэтому в `apps/`, хост-крейтах и
     утилитах не оставляйте новых предупреждений.
   - Тестовые сборки не должны занимать номер ISO: задайте `ISO_PATH` вне `isos/`.
3. **Коммит.** Небольшие целенаправленные коммиты, которые собираются. Не смешивайте
   рефакторинг с новой функцией и не переформатируйте файлы, которые не меняете.
4. **Пул-реквест**: что изменилось и зачем, как проверялось (сборка, ВМ, прошивка, устройства),
   нужная часть serial-журнала. Если меняется вывод на экран, приложите скриншоты.

### Сообщения коммитов

В истории по одной строке на коммит:

```
область: что изменилось, строчными, без точки
```

```
apps/build.ps1: -Only to build, pack and upload selected packages; beeb 0.1.1
ring 3: sound output syscalls (audio_open/write/queued/close/volume)
fs/aeternafs: AeternaFS v2, a copy-on-write filesystem; tools/oosfs
boot: ospab-boot for BIOS, own hybrid ISO, Limine removed
tomato: apt-style commands (update, upgrade, install, remove, search, list, show, files)
```

Сообщения пишутся по-английски.

- Область — каталог, крейт, программа или подсистема (`boot`, `apps`, `tomato`, `drift`,
  `ring 3`, `docs`). Берите слово, которое использовали прежние коммиты этой области.
- Причину и подробности пишите в теле после пустой строки.
- Старые коммиты используют `feat(scope):` и `fix(scope):`. Не смешивайте оба стиля в одном
  пул-реквесте.
- Поднимайте версию в `apps/pkg/<имя>.toml`, когда меняется содержимое пакета.

### Документация

- Английский в `docs/en` основной, `docs/ru` — перевод. Изменение команды, системного вызова
  или формата файла меняет английскую страницу в том же пул-реквесте; русская следует за ней. Если
  вы не пишете по-русски, укажите в пул-реквесте, что перевода нет.
- Держите `README.md` и `README_ru.md` в согласии с таблицами документации.
- Стиль: простой технический язык, короткие предложения, без рекламы и эмодзи. Пишите, чего ещё
  нет. Команды и имена сверяйте с исходниками.

## Чек-лист приёмки

Загрузите сборку и проверьте как минимум:

- [ ] Загрузка заканчивается `[  OK  ] Console: ready`, строк `[ FAIL ]` нет (это проверяет автотест)
- [ ] `uname -a` показывает ожидаемую сборку
- [ ] `ls /` выводит стандартное дерево каталогов
- [ ] `ping 10.0.2.2` работает в QEMU (если меняли сетевой код)
- [ ] `grape /tmp/test.txt` открывается, сохраняет и нормально закрывается (если меняли редактор)
- [ ] `seed status` выполняется (если меняли init)
- [ ] `tomato install` локального `.tmt` и запуск программы (если меняли пакеты или `liboos`)
- [ ] `./build.sh kernel` проходит

## Правила для ИИ-агентов

Правила из `CLAUDE.md` действуют для каждого агента, работающего в этом репозитории. Человек,
использующий агента, отвечает за его действия.

- Меняйте файлы инструментами редактора (Edit и Write), а не скриптами, которые переписывают
  исходники (никаких скриптов правки на Python, sed, awk или PowerShell), и не оставляйте в
  репозитории вспомогательных скриптов. Если правка не применяется, выясните причину: окончания
  строк CRLF, табуляции, управляющие символы.
- Агенты не выполняют `git commit` и `git push`. Это делает ответственный человек.
- Оставайтесь в файлах, которые названы в задаче; остальные могут править другие.
- Не читайте, не печатайте и не копируйте ключ подписи `%USERPROFILE%\.ospab\tmt.key`.
- ROM, образы дисков и другие чужие двоичные файлы не попадают в репозиторий.
- Не занимайте номера ISO в `isos/`: тестовые сборки задают `ISO_PATH` вне него.
- Никогда не убивайте все процессы QEMU, только тот, который запустили сами.

## Отчёт об ошибке

Откройте issue в репозитории GitHub (`github.com/ospab/aeterna`). Укажите:

1. **Сборку.** Вывод `uname -a`:

   ```
   # uname -a
   AETERNA ospab 1.1.0 #181 e8f4f4f+ 2026-10-09 x86_64 ospab.os
   ```

   `+` после коммита означает локальные изменения. Напишите, откуда взяли ISO.
2. **Машину.** VMware или QEMU и версия, BIOS или UEFI, контроллер диска, сетевая карта, звуковая
   карта, режим дисплея, ОЗУ. Для реального железа — модель.
3. **Что вы делали**, шаг за шагом с загрузки. Для программы — пакет и версия (`tomato list`).
4. **Что ожидали и что произошло.** Для программы — код завершения (`echo $?`).
5. **Serial-журнал** целиком, от загрузки до проблемы ([Тестирование](docs/ru/dev/testing.md),
   «Чтение последовательного журнала»). Важнее всего строки `[ WARN ]`, `[ FAIL ]`,
   `[CRITICAL]` и `[FATAL]`. `dmesg` показывает журнал событий ядра.
6. **Скриншот**, если на экране что-то не так; на экране паники виден адрес сбоя.
7. **Повторяется ли**, и была ли та же проблема в предыдущей сборке.

Перед вложением уберите из журналов личные данные.
