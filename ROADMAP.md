# Дорожная карта: от монолита к микроядру

В октябре 2026 решили, что AETERNA станет настоящим микроядром. Текущее состояние кода описано в
[AUDIT.md](AUDIT.md). Каждый этап заканчивается проверкой в QEMU и VMware Workstation.

Отметки в списках: `[x]` сделано, `[ ]` не сделано.

## Зачем эта система

ospab.os не пытается заменить Linux или Windows. Её идея: ОС на правах доступа.

- Без root. Нет всемогущего пользователя и `sudo`. Процесс может только то, на что у него есть
  дескриптор. Первый процесс, `seed`, раздаёт минимум, и права нельзя получить «вообще», только
  на конкретный ресурс.
- Песочница по умолчанию (powerbox). Программа стартует без доступа к файлам, сети и
  устройствам. Файл, который пользователь выбрал в системном окне, она получает одним
  дескриптором, и больше ничего.
- Без копирования (zero-copy). Данные между драйверами, серверами и программами передаются
  дескрипторами общей памяти. Пакет из сетевой карты, страница файла и буфер окна не копируются
  через ядро. Так снимается главный минус микроядра, цена передачи данных между серверами.

Позже на этом фундаменте появятся запись и воспроизведение процессов (на вход процесса попадают
только системные вызовы и сообщения, поэтому его можно проиграть заново) и тензорная нагрузка как
демонстрация zero-copy (AVX-512/AMX, большие страницы).

Порядок такой: этап 0 (фундамент), этап 3 (`seed`, вынос сервисов, rootless), zero-copy в сетевом
и файловом серверах, затем powerbox.

## Что останется в ядре

Только то, что нельзя вынести:

- физические страницы и адресные пространства;
- потоки, планировщик, переключение контекста;
- IPC: синхронные сообщения (вызов и ответ) и асинхронные уведомления;
- передача и разделение памяти между процессами через IPC;
- прерывания, которые доставляются драйверам как уведомления;
- права доступа: у каждого процесса своя таблица дескрипторов, любое действие требует дескриптора.

Остальное станет серверами в ring 3: драйверы, сеть (с OSTP), файловые системы, консоль, init.

## Этапы

### Этап 0. Фундамент ядра
Без этого ring 3 опасен. Пункты 1–6 из AUDIT.md.

1. [x] Физический аллокатор с освобождением (bitmap), обнуление выделенных страниц.
2. [x] Свой стек ядра у каждого потока; `TSS.RSP0` и стек SYSCALL переключаются вместе с потоком.
   Блокирующий системный вызов теперь безопасен. Заодно сделали состояние FPU/SSE у каждой
   задачи, единое правило `swapgs` на входе в ring 3 и выходе из него, round-robin при равных
   приоритетах.
3. [x] Кольцо не зависит от приоритета: `spawn_named` создаёт только потоки ядра,
   ring 3 создаёт только `spawn_user_task`.
4. [x] `copy_from_user` / `copy_to_user` во всех системных вызовах с указателями, SMEP + SMAP
   (если процессор умеет); `mmap`/`munmap` работают с памятью самого процесса.
5. Процесс как объект: [x] адресное пространство, стек ядра и собственные страницы освобождаются
   при выходе; [x] таблица дескрипторов (`core/object.rs`); [ ] FD-таблица на процесс.
6. [ ] Блокировки вместо `static mut`.
6а. [x] XSAVE вместо FXSAVE: размер области берётся из CPUID 0xD (с проверкой, иначе откат на
    FXSAVE), выравнивание 64 байта. Тест: две задачи держат разные значения в ymm0/ymm15 при
    вытеснении.

Проверка: при загрузке выполняются тесты ring 3 (smoke, два процесса одновременно с блокировкой
в ядре, проверка указателей и `mmap`), а потом проверка, что не осталось занятых страниц.

### Этап 1. Программы в ring 3
7. [x] ELF-загрузчик в ядре (`core/elf.rs`): сегменты с правами R-X / R-- / RW- и NX,
   стек с `argc`/`argv`/`auxv`.
8. [x] `user/x86_64-unknown-oos.json` и liboos (`user/liboos`: `_start`, системные вызовы,
   куча через `mmap`, `print!`, panic). Программы собираются отдельным workspace `user/`.
9. [x] Первая программа, `user/hello` на Rust, запускается из ядра при загрузке. Пока она
   встроена через `include_bytes!`; загрузка из файловой системы войдёт в этап 3.

### Этап 2. IPC и права доступа
10. [x] Объекты ядра и дескрипторы с правами (READ/WRITE/DUP/TRANSFER): процесс, поток, канал,
    уведомление, ответ (Reply); [x] память, MMIO, прерывание, порты, ресурс DMA (пункты 12–13);
    [ ] адресное пространство как объект.
11. [x] Синхронный IPC (вызов и ответ) с передачей дескрипторов, блокирующий приём без цикла
    ожидания, уведомления. Описание: [docs/ru/syscall-abi.md](docs/ru/syscall-abi.md); обёртки
    лежат в `liboos::ipc`; тест: `user/ipcsrv` и `user/ipcclient` (запуск параметром ядра
    `selftest=ipc`).
12. [x] Разделяемая память через дескрипторы: объект MemoryRegion (`mem_create`/`mem_map`/`mem_unmap`,
    права MAP/EXEC/PHYS, NX по умолчанию, W^X). У страниц есть счётчик ссылок (дескрипторы и
    отображения), при выходе процесса они освобождаются. DMA выделяется через
    `mem_create_contig` и только с дескриптором Resource(DMA). SMR с сырыми физическими адресами,
    `dma_alloc`, сырой ввод-вывод в порты (60/61/62) и `vfs_register` из системных вызовов
    убраны. Тест: `user/memtest` (`selftest=mem`).
13. [x] Оборудование как дескрипторы: Interrupt (линия IRQ превращается в Notification, маска
    держится до `irq_ack`), IoPortRange (карта разрешений ввода-вывода в TSS), MmioRegion
    (отображение без кэша). Создаёт их только корень (ядро при загрузке), драйвер получает их
    начальными дескрипторами. Проверка: драйвер COM2 в ring 3 (`user/uartdrv`, `selftest=mem`,
    нужен второй `-serial`). [ ] MSI.

### Этап 3. Вынос сервисов из ядра
Идём от простого к сложному, по одному сервису. После каждого шага ядро должно оставаться рабочим.

14. `seed` — первый настоящий процесс. Он запускает остальных и перезапускает упавших. Только
    у него корневые права: он создаёт объекты железа, раздаёт их, а лишние после старта
    сбрасывает.
15. Консоль: клавиатура и фреймбуфер уходят в сервер консоли, `plum` становится обычной
    программой. С этого момента в системе нет root: оболочка — процесс со своими дескрипторами.
16. Хранилище: AHCI/NVMe становятся серверами-драйверами, VFS становится сервером файловой
    системы. Страницы файлов отдаются клиентам дескрипторами памяти (zero-copy).
17. Сеть: драйверы NIC и сетевой стек становятся серверами. Пакеты ходят в буферах общей памяти,
    без копирования между драйвером, стеком и приложением.
18. Звук, мышь, остальное. DOOM — обычная программа.
19. В ядре не остаётся драйверов, кроме таймера, контроллера прерываний и отладочного serial.
19а. Powerbox: программы стартуют без доступа к файлам и сети, а системное окно выбора файла
     выдаёт программе дескриптор на один файл.

### Этап 4. Свой загрузчик
20. UEFI-загрузчик на Rust вместо Limine; образ диска GPT + FAT32 собирается без WSL.

### Этап 5. OSTP
21. `ostp-core` в режиме `no_std + alloc`.
22. OSTP как туннельный интерфейс в сетевом сервере.

## Отложено
- SMP (несколько ядер процессора): после этапа 2.
- Полноценный `std` для программ: после этапа 3.
